# SNAP ABAWD work rules screening: Docassemble package

A port of the MLRI web screener, for Court Forms Online. They host through the Suffolk LIT
Lab Document Assembly Line and told us in July 2026 that anything on their site has to be a
Docassemble interview, which is what this is for.

## What is verified and what is not

This distinction matters more than anything else in this README, so it comes first.

**The decision logic is verified.** `snap_abawd.py` decides the same things as the
JavaScript reference, `court-forms/snap-screening-logic.js`. Proven, not assumed:
`tests/test_snap_abawd_parity.py` reads `decision-spec.json`, which is generated from the
JavaScript, and checks every worked example, all 32 combinations of the housing follow-up
plus the none-of-these answer, every single-answer exemption, the work and disability
options, outcome precedence, and the order reasons come out in. 22 tests across the two
files. They were mutation-checked: breaking a reason string, removing the housing health
override, or dropping a work option each makes them fail.

**The interview is not verified.** `data/questions/snap_abawd.yml` has never been run,
because there is no Docassemble server where it was written. It parses as valid YAML, all 19
documents, and every screen its `mandatory` block references is defined somewhere in the
file. That is the extent of it. Expect to fix things on first run.

**The ALKiln feature file has not been run either**, for the same reason. It is generated
from the same worked examples the Python tests use, so it should pass once there is a server.

## Running the tests

No Docassemble needed:

```
python docassemble-snap-abawd/tests/test_snap_abawd_parity.py
python docassemble-snap-abawd/tests/test_good_cause_text.py
```

They read `decision-spec.json` from the repository root. Regenerate it after any change to
the JavaScript, with `scripts/decision-spec.js`, and these tests immediately start checking
the new behaviour. That is the point: the expectations live with the reference
implementation, not here.

## What is generated, and what to edit

Do not hand-edit these. Regenerate them, or the wording drifts from the web screener and
from `SCREENER-COPY.md`, which is what the author actually reviews.

| File | Generated by |
|---|---|
| `data/questions/snap_abawd.yml` | `scripts/gen-docassemble.js` |
| `data/sources/snap_abawd.feature` | `scripts/gen-docassemble.js` |

`snap_abawd.py` and the tests are hand-written and safe to edit, though the reason strings
and good cause wording in the module have to stay identical to the reference. The tests
enforce that.

## Design decisions worth knowing

**Variable names are the JavaScript ids unchanged**, camelCase and all: `child14`,
`housingFollowup`, `substanceUse`. They are valid Python identifiers, and keeping them
identical means the dictionary handed to the decision module needs no translation layer that
could itself be wrong.

**The none-of-these answer is an explicit choice with the value `__none`**, not
Docassemble's built-in `none of the above`. The decision logic treats "none of these apply"
and "nothing checked" as opposite answers on the housing follow-up, and the built-in gives
no distinct value to tell them apart. A port that collapses them is wrong in a way that
changes who comes out exempt. The exhaustive table in `DECISION-SPEC.md` shows it.

**Every field is `required: False`**, because every question in this screening is optional.
It also keeps the variables defined, so the decision code never triggers a question of its
own.

**The skip decision uses `partial_answers`, not `collected_answers`.** `collected_answers`
includes the good cause answer, so testing it there would need the answer before deciding
whether to ask the question. Nothing that decides the skip depends on good cause.

**The statement is an inline `attachment` with markdown content**, not a DOCX template, so
the package carries no binary and can be reviewed as text.

## Recommended next steps

Run it. Everything above is an argument that it should work, which is not the same thing.

Turn on the AssemblyLine include, commented at the top of the YAML. That brings Court Forms
Online branding, `ALDocument`, and their tested question library. It was left off so the
file runs on a plain server without the dependency.

Fill DTA's own SNAP Work Rules Exemption Self-Declaration Form instead of generating a
letter. The URL is in `LINKS.exemptionForm` in the reference. A guided interview that
completes a real agency form is what the Assembly Line pipeline is built for, and it is a
stronger pitch than a generated statement.

Settle the retention question. The web screener keeps answers in the browser for 24 hours
and transmits nothing, and says so on the page. On a Docassemble server they become session
data under the host's policy. That changes what the tool can honestly claim, not just where
it runs, and the questions here cover pregnancy, disability, domestic violence, and personal
safety.

Decide about the big Yes/No tiles. They are a deliberate departure from stock Docassemble
question screens and the reason the web version reads better than a default interview.
Keeping them means custom CSS in this package.

## Still open, and not ours to settle

The income and hour thresholds are settled: confirmed 2026-08-07 against MLRI's SNAP Advocacy
Guide, May 2026, Part 2, Question 61, which gives all three of them including the 30 hours a
week below minimum wage. The guide is in `reference/` and the citation is `THRESHOLD_SOURCE`
in the JavaScript reference.

What is still open is the housing follow-up. The same question in the guide says those
screening answers are not an automatic exemption and that DTA assesses inability to work from
them. The port mirrors the JavaScript, which currently returns a determinate answer, so both
will need the same change. `DECISION-SPEC.md` has a Citation column against every rule and the
rows are still blank; Question 61 now covers most of them.

The age wording was settled on 2026-08-03 and now reads "18 through 64"
everywhere. MLRI's ABAWD article says "between 18 and 65", which does not say whether a
65-year-old is included; the federal rule caps at 64, with 65 and over exempt by age. The
screener states the range unambiguously rather than mirroring the looser phrasing. That
reading of the rule is still worth an expert's confirmation.
